# 0008. Database schema conventions

- Status: Accepted
- Date: 2026-10-07

## Context
The backend stores financial data for many users in one PostgreSQL database and has to
mirror the engine's domain types. One missed ownership check in a service could link
one user's data to another's, and old plans must stay explainable after the bills and
goals they mention change or are deleted.

## Decision
- **Tenant guard in the database.** Every user-owned table has `user_id` (cascading
  from `users`) and `UNIQUE (user_id, id)`. A row that points at another user-owned row
  uses a composite foreign key `(user_id, x_id) -> parent (user_id, id)`, so PostgreSQL
  rejects a cross-user reference whatever the service code does. Where history must
  outlive its target, the key uses `ON DELETE SET NULL (x_id)` (PostgreSQL 15+), which
  clears the target and never the owner.
- **Typed foreign keys, not polymorphic ones.** Reserves and allocations have one
  nullable foreign key per target type (`bill_id`, `goal_id`, ...) and a CHECK that only
  the one matching their `kind` or `tier` is set.
- **Enums are VARCHAR with a CHECK**, holding the engine's stable string values. Native
  PostgreSQL enums are hard to change in migrations.
- **Engine rules are repeated as CHECK constraints** where they concern one row (positive
  amounts, day-of-month ranges, schedule parameters, one emergency goal per user). Rules
  that need dates or several rows stay in the engine.
- **Plans are immutable snapshots.** `paycheck_plans`, `allocations` and `goal_projections`
  copy every fact needed to explain a plan later (target names, the full `Basis`),
  along with `engine_version` and `input_hash`. Only a plan's status changes.
- **Deletes:** setup data can be deleted, and its plan history survives through the SET NULL
  keys above. Paychecks and plans are history, so an income source with paychecks cannot
  be deleted (RESTRICT). Whether to archive or refuse in that case is decided in 2C.
- **Migrations are reviewed, not trusted.** Autogenerated revisions are edited by hand
  and never import the app. A test compares the migrated schema with one built from the
  models, using the PostgreSQL catalog, which also catches CHECK constraints and index
  predicates that Alembic's autogenerate does not compare.

## Consequences
- Cross-user links are impossible, not just unlikely.
- Each parent table carries one extra unique index, and child rows repeat `user_id`.
- Adding a value to an engine enum needs a migration that alters the CHECK; the schema
  test fails until it exists.
- Schema changes take two steps (model, then a reviewed migration), enforced in CI by
  `alembic check` and the schema tests.
